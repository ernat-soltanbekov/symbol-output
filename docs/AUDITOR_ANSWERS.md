# Ответы и объяснения для аудита

Здесь собраны ответы на вопросы из ТЗ и вероятные уточнения. Ответы описывают фактическую реализацию проекта.

Для воспроизводимых команд есть [матрица требований](AUDIT_REQUIREMENTS.md). Основные исходники: [CLI](../internal/cli/cli.go), [генератор](../internal/generator/generator.go), [запись файла](../internal/writer/writer.go), [проверка файла](../internal/verifier/verifier.go).

## Пять вопросов из ТЗ

### 1. Где файл записывается и проверяется? Зачем перечитывать его?

В обычном режиме с `--output` функция `cli.Run` получает готовый рисунок от генератора и вызывает `writer.Write`. При `--verify` проверка запускается только после успешной записи: `writer.Write` → `verifier.Verify` → `readRegularFile` → `os.ReadFile`.

Строка в оперативной памяти показывает, что программа хотела записать. Повторное чтение показывает байты, которые сейчас доступны по пути результата. Это позволяет проверить реальный файл, а не просто ещё раз подтвердить правильность переменной. Ошибка записи останавливает работу до проверки: нельзя сообщать об успешном создании файла, который не удалось сохранить.

В `verifier.Verify` передаются ожидаемые ширины текстовых рядов. Они служат описанием нужной геометрии. Сами проверяемые линии и размер берутся из повторно прочитанного файла.

Существует отдельный режим `--tamper-check`: он проверяет **уже существующий** файл. В этом режиме `writer.Write` вообще не вызывается. Иначе программа сначала затёрла бы изменения, а потом объявила файл неизменённым. При сочетании `--verify --tamper-check` обе проверки читают существующий файл.

### 2. Что доказывает каждая из пяти проверок?

| Проверка | Что именно проверяется | Практический пример нарушения |
|---|---|---|
| Readable | По пути есть обычный файл, допустимый по ограничениям, и его удалось прочитать | Файл отсутствует, недоступен, является каталогом или ссылкой |
| Line count | Число прочитанных линий равно `8 × число текстовых рядов` | Удалена линия или добавлена девятая пустая линия к `hello` |
| Consistent width | В каждом блоке из восьми линий их длины совпадают | Из одной линии удалён символ |
| Padding | Каждая линия имеет точно ожидаемую ширину своего ряда и состоит из печатного ASCII | Ко всем линиям добавлен лишний пробел; ширина стала одинаковой, но неправильной |
| Size | Число прочитанных байтов равно сумме длин прочитанных линий плюс один LF на каждую | Пропал последний перевод строки |

Одна проверка не обязана обнаруживать все виды повреждения. Например, если удалить целую линию вместе с её LF, формула размера для оставшихся линий ещё может сойтись. Отсутствующую линию обнаружат проверки количества и геометрии.

Если чтение невозможно, программа не придумывает содержимое: все пять проверок отмечаются как неуспешные, итог — `0/5 (Corrupted)`, а отчёт объясняет ошибку чтения.

### 3. Как вычисляются ожидаемое число линий и размер файла?

Пусть после обработки переносов есть `R` текстовых рядов, а их ширины — `w₁, w₂, …, wᵣ`. Высота любого символа равна восьми линиям. Ширина ряда — сумма ширин всех символов этого ряда из выбранного шрифта.

```text
Число линий рисунка = 8 × R
Размер правильного рисунка = Σᵢ 8 × (wᵢ + 1) байт
```

Единица в скобках — байт LF после каждой линии, в том числе после последней. Между рядами не вставляется дополнительная девятая линия.

Для `hello` со шрифтом `standard` один ряд имеет ширину 31:

```text
Линий: 8 × 1 = 8
Байтов: 8 × (31 + 1) = 256
```

Для `First\nTest` со шрифтом `shadow` ширины рядов — 39 и 38. Они различаются, и это нормально:

```text
Линий: 8 × 2 = 16
Байтов: 8 × (39 + 1) + 8 × (38 + 1) = 320 + 312 = 632
```

В реализации пятой проверки применяется формула именно к прочитанным линиям: `Σ(длина линии в байтах + 1)`. Она проверяет устройство файла и последний LF. Совпадение геометрии с исходным текстом проверяется отдельно количеством линий и padding. Это разные проверки, их не нужно смешивать.

У полностью пустого аргумента `''` нет текстовых рядов: результат — 0 линий и 0 байт. В непустом вводе пустой ряд имеет ширину 0, но всё равно занимает восемь LF и восемь байт.

### 4. Почему нормальные пробелы справа не считаются лишним padding?

Шрифт рисует каждый символ в прямоугольнике. Пробелы внутри этого прямоугольника, включая пробелы справа, занимают реальные колонки рисунка. Например, у `hello` две нижние линии состоят из 31 пробела каждая. Это корректные линии шириной 31.

Проверка не вызывает `strings.TrimSpace` или удаление пробелов справа. Она сравнивает `len(line)` с шириной ряда, вычисленной по шрифту. Для ширины 31 линия из 31 пробела допустима, а из 32 — уже нет. Линия из 30 пробелов тоже неправильная: из рисунка удалена колонка.

Почему нужны и consistent width, и padding? Если добавить один пробел ко всем восьми линиям, они останутся одинаковой ширины. Проверка consistent width пройдёт, но padding обнаружит несоответствие ожидаемой ширине. Обратная ситуация с удалением одной колонки из всех линий обнаруживается так же.

### 5. Как формируется Integrity Score и verdict?

Каждая из пяти проверок имеет значение успеха. Score — количество успешных проверок, без весов и округлений.

| Число успехов | Вердикт из ТЗ | Значение |
|---|---|---|
| 5 | `Valid` | Все пять структурных проверок прошли |
| 4 | `Acceptable` | Одна проверка не прошла |
| 0–3 | `Corrupted` | Не прошли две проверки или больше |

`Acceptable` — заданное ТЗ название результата, а не обещание, что файл полностью исправен. Программа возвращает ненулевой код завершения при любом результате ниже `5/5`, чтобы скрипт мог обнаружить нарушение. Например, потеря последнего LF может дать `4/5 (Acceptable)` и код 1.

Score не является вероятностью, оценкой безопасности или процентом сохранённых символов. Это ровно число пройденных проверок. Результат `5/5` подтверждает структуру файла; точное содержание сравнивается бонусной проверкой.

## Ввод, флаги и шрифты

### Какие аргументы допустимы?

```sh
go run . 'hello'
go run . 'hello' shadow
go run . --output=banner.txt 'hello' standard
go run . --output=banner.txt 'hello' standard --verify
go run . --output=banner.txt 'hello' standard --tamper-check
go run . --output=banner.txt 'hello' standard --verify --tamper-check
```

Без указанного шрифта применяется `standard`. Без `--output` рисунок печатается в stdout. При обычной записи без `--verify` stdout не заполняется служебным отчётом: в файл записывается рисунок.

Флаги могут стоять перед текстом или после него. `--output` принимается только как один аргумент `--output=<путь.txt>`. Путь обязан быть непустым, иметь расширение `.txt` и не содержать NUL. Раздельная запись `--output banner.txt`, неизвестные флаги, дубли флагов, лишние позиционные аргументы и неизвестный шрифт приводят к Usage. Для `--verify` и `--tamper-check` обязательно указать `--output`.

### Почему разбор аргументов написан отдельно, а не через пакет flag?

ТЗ требует точную форму `--output=...` и разрешённое расположение проверочных флагов после текста и шрифта. Отдельная небольшая функция `cli.Parse` прямо проверяет эти правила, не принимает дополнительные варианты по умолчанию и тестируется без запуска отдельного процесса.

Самостоятельный разбор здесь ограничен несколькими известными флагами. Это не универсальная библиотека аргументов.

### Как передать строку, начинающуюся с дефиса?

Разделитель `--` завершает разбор флагов. После него аргументы считаются текстом и, при наличии, именем шрифта:

```sh
go run . -- '-hello' standard
go run . --output=dashes.txt -- '--verify' standard
```

Во втором примере `--verify` — текст рисунка. Настоящие опции нужно поставить до разделителя.

### Почему нужны одинарные кавычки для `#$%`?

Оболочка обрабатывает аргументы до запуска Go-программы. В двойных кавычках знак `$` может начать подстановку переменной. Одинарные кавычки передают специальные символы буквально:

```sh
go run . --output=special.txt '123 -> #$%' standard --verify
```

### Почему поддерживается ASCII, а не кириллица и emoji?

Три заданных шрифта содержат ровно 95 печатных символов с кодами 32–126: от пробела до `~`. Для кириллицы и emoji в этих таблицах нет рисунков. Генератор сообщает понятную ошибку для неподдерживаемого символа, вместо обращения за пределы таблицы или молчаливой замены.

Также отвергаются табуляция, CR, NUL, DEL и недопустимые байты UTF-8. Настоящий LF разрешён как разделитель текстовых рядов. CRLF в **таблицах шрифтов** нормализуется при чтении; CR в **пользовательском тексте** не превращается автоматически в разрешённый символ.

### В Go длина строки — это символы или байты?

`len(string)` возвращает число байтов. Для печатного ASCII каждый символ занимает один байт, поэтому длина в байтах совпадает с количеством колонок этого рисунка. Для UTF-8 такое равенство в общем случае неверно: например, `é` занимает несколько байтов. Проект не пытается рисовать UTF-8 заданными ASCII-шрифтами.

LF занимает один байт. Поэтому формула размера использует `+1`, а не `+2`. Файл результата всегда записывается с LF, без CRLF.

### Как обрабатываются переносы и пустой ввод?

Генератор превращает буквальную пару `\n` в настоящий LF, а затем делит непустой текст по LF. Это правило работает одинаково для `"A\nB"`, уже содержащего настоящий перенос, и аргумента `'A\nB'` из оболочки.

| Ввод | Текстовых рядов | Линий рисунка |
|---|---:|---:|
| `''` | 0 | 0 |
| `'A'` | 1 | 8 |
| `'A\nB'` | 2 | 16 |
| `'A\n'` | 2 | 16 |
| `'\n'` | 2 пустых | 16 |
| `'A\n\nB'` | 3 | 24 |

Полностью пустой ввод трактуется как отсутствие текста для совместимости базового проекта. Остальные пустые ряды сохраняются. Это явно выбранная политика; она не замалчивается и покрыта тестами.

У буквальной пары `\n` есть специальный смысл. Если требуется нарисовать отдельно обратную косую черту и сразу после неё букву `n`, текущий интерфейс не предоставляет отдельного способа экранирования этой пары.

### Почему нет девятой пустой линии после `hello`?

Некоторые иллюстрации `cat -e` в приложенном аудите показывают ещё один `$` после восьми линий. Однако обязательный пример проверки требует ровно восемь линий и 256 байт. Дополнительный LF дал бы девять линий и 257 байт. Проект следует прямому числовому требованию ТЗ.

### Откуда берутся шрифты и зачем embed?

В проекте присутствуют `standard.txt`, `shadow.txt`, `thinkertoy.txt`; происхождение записано в [источниках шрифтов](FONT_SOURCES.md). При сборке [banners.go](../banners.go) включает их байты в исполняемый файл через `embed.FS` из стандартной библиотеки.

Поэтому запуск готового бинарника из другого каталога не требует копировать рядом шрифты и не зависит от относительного пути к репозиторию. Изменение исходного `.txt` после сборки не меняет уже собранный бинарник: для применения нового шрифта нужна новая сборка.

`generator.Parse` проверяет формат таблицы: 95 символов, восемь линий на символ, пустые разделители, одинаковую ширину линий одного символа, допустимый ASCII и конечный LF. Пробелы не удаляются. Повреждённая таблица не используется как корректный шрифт.

## Файлы, ошибки и устройство программы

### За что отвечает каждый пакет?

| Часть проекта | Ответственность |
|---|---|
| [main.go](../main.go) | Передать аргументы, встроенные шрифты и потоки вывода в CLI, завершиться с его кодом |
| [internal/cli](../internal/cli/cli.go) | Проверить аргументы и организовать порядок действий |
| [internal/generator](../internal/generator/generator.go) | Проверить шрифт, вход и сформировать рисунок с ширинами рядов |
| [internal/writer](../internal/writer/writer.go) | Сохранить готовый результат и обработать ошибки записи |
| [internal/verifier](../internal/verifier/verifier.go) | Прочитать файл, выполнить пять проверок, сравнить изменения и вывести отчёты |

Так отдельную логику можно проверить независимо. Генератор не пишет файлы, writer не определяет форму букв, verifier не создаёт проверяемый файл. Дополнительные слои и внешние библиотеки для этой задачи не нужны.

### Почему запись идёт через временный файл?

`writer.Write` создаёт временный файл в каталоге результата, записывает весь рисунок, проверяет ошибки и число записанных байтов, устанавливает права, вызывает `Sync`, закрывает файл и заменяет целевой путь через `os.Rename`.

На используемой файловой системе замена внутри одного каталога даёт читателю целый старый или целый новый файл. Это защищает существующий результат от частично выполненной записи, например при ошибке до `Rename`. Временный файл убирается при выходе из функции; ошибки закрытия и очистки тоже учитываются.

Это свойство не означает гарантированной сохранности при любом отключении питания. Здесь не выполняется `Sync` самого каталога после переименования. Поведение `Rename` и файловых прав зависит от ОС и файловой системы. Также нет блокировки между несколькими процессами: при конкурентной записи итог соответствует одной завершённой записи, и последующая успешная замена может вытеснить предыдущую.

### Какие ошибки обрабатываются?

Ошибки создания, записи, короткой записи, изменения прав, синхронизации, закрытия, проверки пути, переименования и чтения передаются наверх с контекстом. Ошибка не превращается в успешный отчёт. В CLI она печатается в stderr; рисунок и отчёты выводятся через stdout.

Необходимый родительский каталог должен уже существовать. Writer не создаёт его автоматически. Он отвергает каталог, символическую ссылку и другие неподходящие виды файла в качестве результата. Обычные права существующего файла сохраняются; файл без битов записи не заменяется. Новый результат получает права `0644`.

Writer проверяет целевой путь перед подготовкой и ещё раз перед заменой. Это уменьшает риск незамеченной смены вида файла, но не устраняет все гонки, если другой процесс специально меняет пути между отдельными системными вызовами. Проект не заявляет защиту от всех действий враждебного процесса с доступом к тому же каталогу.

### Что защищает исходные шрифты и `.git`?

Обычная запись отклоняется для пути с компонентом `.git`. Также защищается существующий файл с именем одного из трёх шрифтов, если его байты точно совпадают со встроенной таблицей. Само имя `standard.txt`, `shadow.txt` или `thinkertoy.txt` допустимо для обычного результата, который не является исходной таблицей.

Эта проверка помогает избежать случайной порчи файлов проекта. Она не заменяет права файловой системы и не является полной защитой любых возможных ссылок, переименований и изменений каталогов другим процессом.

### Какие ограничения размера выбраны и зачем?

| Объект | Ограничение |
|---|---:|
| Исходный текст | 1 МиБ, то есть `1 << 20` байт |
| Текстовые ряды после обработки переносов | 10 000 |
| Сформированный рисунок | 64 МиБ, то есть `64 << 20` байт |
| Читаемый файл verifier | 64 МиБ |
| Линии читаемого файла verifier | `1 << 20`, то есть 1 048 576 |

Размер результата рассчитывается до выделения большого буфера. Отдельное ограничение числа рядов защищает от огромного количества пустых строк. Ограничение числа линий проверяемого файла нужно потому, что миллион LF занимает примерно 1 МиБ, но разделение на строки дополнительно создаёт большой список элементов.

Verifier проверяет вид и размер файла перед `os.ReadFile`, затем проверяет размер прочитанных данных и количество линий перед разделением. Это ограничения для предсказуемой обычной работы. Если файл меняется конкурентно во время чтения, предварительный размер сам по себе не гарантирует жёсткий предел всех временных выделений памяти внутри `os.ReadFile`.

### Что означают коды завершения?

| Код самого бинарника | Значение |
|---|---|
| 0 | Операция успешна; все запрошенные проверки прошли |
| 1 | Ошибка ввода/генерации/файлов/вывода, проверка ниже `5/5` или обнаруженные изменения |
| 2 | Неправильная форма аргументов; показан Usage |

`go run` — оболочка запуска Go: она может представить ошибку дочерней программы своим кодом и строкой `exit status`. Если проверяется точный код 2, нужно запускать собранный бинарник.

## Проверка изменений и границы доверия

### Чем tamper-check отличается от verify?

`--verify` проверяет структуру: число линий, геометрию, padding и LF/размер. Если заменить `|` на `#` без изменения длины, структура останется корректной и все пять проверок могут пройти.

`--tamper-check` заново получает рисунок из того же текста и выбранного шрифта, читает существующий файл и сравнивает соответствующие линии по байтам. Поэтому замена одного символа без изменения размера обнаруживается.

```sh
go run . --output=banner.txt hello standard
go run . --output=banner.txt hello standard --tamper-check
```

Первый вызов создаёт результат; второй проверяет, совпадает ли он с новой генерацией. Если файл отсутствует, проверка изменений возвращает ошибку. Она не создаёт отсутствующий файл и не перезаписывает существующий.

### Как считаются номера отличающихся линий?

Нумерация начинается с 1. Проверяются позиции до большего из двух количеств линий. Изменённая линия, лишняя линия на диске и отсутствующая ожидаемая линия отмечаются как различия. Поэтому если у эталона восемь линий и на диске добавлен LF, сообщение указывает линию 9.

Разделение для tamper сохраняет LF в составе каждой линии. Если после восьмой линии удалён только последний LF, отличается линия 8, хотя видимые символы не поменялись. Пробел, CR и любой другой байт также участвуют в сравнении.

При вставке строки в середину последующие линии сравниваются по новым позициям и тоже могут отличаться. Это сравнение соответствующих номеров строк, а не алгоритм поиска минимального набора редакторских изменений.

### Можно ли проверить повреждённый файл без перезаписи?

Да, с сочетанием флагов:

```sh
go run . --output=banner.txt hello standard --verify --tamper-check
```

Обе проверки читают существующий файл. Вызов только с `--verify` сначала формирует и записывает новый результат, а затем проверяет его, как требует основной сценарий ТЗ.

### Почему это называется AI, если нейросети нет?

В ТЗ AI прямо описан как проверка измеримых свойств по правилам. Здесь реализован такой алгоритм: пять условий, подсчёт успехов и сравнение с новой генерацией. Нет модели, обучения, сетевого запроса или внешней AI-библиотеки. Используются только стандартные пакеты Go.

### Является ли результат криптографической подписью?

Нет. Повторное чтение подтверждает свойства байтов, доступных локальной программе в момент проверки. Tamper сравнивает их с текущими входом и встроенным шрифтом. Это полезная локальная проверка согласованности, а не независимое доказательство авторства, даты создания или неизменности за всё время существования файла.

Если одновременно изменить входные данные, код и файл так, чтобы они снова совпадали, такая проверка не установит прежнее содержимое. Здесь нет секретного ключа, подписи, доверенного журнала или сохранённого исторического эталона. При другом исходном тексте или шрифте tamper закономерно покажет различия.

## Тесты и демонстрация понимания

### Какие случаи проверяются тестами?

Генератор проверяется на независимом эталоне `hello`, всех 95 печатных ASCII во всех трёх шрифтах, разных переносах, пустом вводе, неподдерживаемых символах, повреждённых шрифтах и ограничениях размера.

Writer проверяется на создании и полной замене файлов, сохранении прав, отказе для каталогов и ссылок, отсутствии родительского каталога, защищённом каталоге, превышении размера и конкурентных записях.

Verifier проверяется на чистых и повреждённых файлах: отсутствующей линии, лишней линии, разной ширине, одинаковых лишних колонках, удалённом последнем LF, пустых рядах, ошибках чтения, слишком большом числе линий, точных номерах изменений и ошибках вывода отчёта.

CLI проверяется на разрешённых и неправильных аргументах, форме Usage, стандартном stdout, записи и проверках, сохранении файла при tamper, неподходящих целях записи и ошибках потоков вывода. Есть fuzz-тесты генератора и verifier: автоматически меняющиеся входы помогают искать необычные случаи и паники.

### Зачем stress, race и конкурентная запись?

Повторные запуски помогают заметить нестабильность. `go test -race` ищет гонки доступа к памяти Go. Тест конкурентной записи проверяет, что итоговый файл содержит целую полезную нагрузку одной записи, а не смесь нескольких рисунков. Ограничения защищают от чрезмерных обычных входов.

Race detector не доказывает отсутствие гонок файловой системы между процессами. Конкурентный тест не гарантирует заранее выбранного победителя: при нескольких успешных заменах конечный файл принадлежит одной из них. Stress и fuzz расширяют покрытие, но конечное число запусков не может доказать устойчивость к любой ситуации.

### Как проверить проект самому?

```sh
go test ./...
go test -race ./...
go vet ./...
gofmt -l .
```

Повторный запуск и ограниченные по времени fuzz-проверки:

```sh
go test ./... -count=10
go test ./internal/generator -run='^$' -fuzz=FuzzGenerate -fuzztime=5s
go test ./internal/verifier -run='^$' -fuzz=FuzzVerify -fuzztime=5s
```

`gofmt -l .` должен не вывести имён файлов. Команды являются способом повторной проверки; сведения о реально выполненных проверках находятся в [отчёте проверки](TEST_REPORT.md).

### Почему go.sum может отсутствовать?

Проект использует стандартную библиотеку, поэтому нет внешних зависимостей, для которых Go нужно хранить контрольные суммы модулей. `go.mod` задаёт имя проекта и минимальную версию Go. Проверить список модулей можно через `go list -m all`.

### Что показать аудитору на новом примере?

Нужно выбрать текст и шрифт, посчитать текстовые ряды, объяснить сумму ширин символов для каждого ряда и применить формулы. Затем можно создать файл с `--verify`, сверить числа с отчётом и изменить одну линию без изменения длины. Структурная проверка при этом может остаться `5/5`, а tamper укажет номер изменения. Это демонстрирует понимание двух разных задач проверки.

Если аудитор предложит другой пример, не нужно угадывать ширину. Она зависит от символов и шрифта. Следует вычислить её по таблице либо объяснить, где генератор получает этот размер, а затем независимо проверить число линий и байтов.
